# Dispatch Identity Store — Implementation Result

- Module: `response_verification/dispatch_store.py` — durable reservation store implementing the `RESPONSE-VERIFICATION-001-replay-acceptance.md` next-slice contract: explicit state machine (reserved → dispatching → observed-success / observed-failure / unknown / cancelled; illegal transitions refused), authorization binding (task + approved-request digest + destination + artifact digest + claim class + rendering → logical delivery key; changed binding = different identity, original dedupe untouched), atomic cross-process reservation (flock + fsync append), monotonic fencing tokens (stale owner fenced after lease transfer via `adopt()`), lease expiry denies send with no auto-retry, `dispatching`/unknown never adoptable (possible send in flight → held), native delivery-ID capture separate from transport ack, torn/corrupt/binary store line → `storage_refused` for ALL keys, unknown schema version or novel state string → `schema_refused`, unwritable store → `storage_refused`. Same-UID owner names are coordination labels, not authenticated principals.
- Terminal semantics: `observed-success`, `unknown`, `observed-failure`, `cancelled` are terminal for the same binding key; retry after failure/cancel requires a NEW authorization identity (new approved-request digest), which by construction is a different logical key. `unknown` is held forever — no API path converts it to a resend.
